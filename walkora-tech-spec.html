Walkora — Tech Spec

Section 1

Overview & engineering principles

This document specifies how Walkora is built. Product behaviour, priorities, and release phasing are owned by the PRD; every design below cites the PRD requirement IDs it implements (e.g. TRK-05). Where the PRD leaves a decision open (§19 of the PRD), this spec states the working assumption and flags it in §19 here.

Offline-first, always

The phone is the primary tracker and must work with no network and no account. Every read hits local storage first; every mutation goes through a durable outbox. The server is a synchronization and social layer, not a dependency for core value. (ACC-01, TRK-03)

Trust the number

Every displayed total is explainable: which source, when synced, how conflicts were resolved. Dedup and timezone logic are pure, exhaustively unit-tested functions. (TRK-04, TRK-06, WBL-04)

Server-side authority

The client renders; the server decides. Authorization, rate limits, fairness checks, and privacy filters run server-side on every protected operation — client checks are UX, never security. (PRD §13)

Boring at MVP, ready to scale

A modular monolith with enforced module boundaries ships fastest and can be split later along the same seams. No microservices, no event bus, no Kubernetes until a measured need exists. (ADR-02)

Privacy as architecture

Data minimization, purpose-scoped tables, consent records, and export/deletion pipelines are schema-level concerns designed before the first social feature ships. (PRD §13)

Accessibility is a gate

TalkBack, font scaling, and contrast checks run in CI; a release that regresses them does not ship. (PRD §12)

Section 2

System architecture

One Android client, one backend deployable (modular monolith), one relational source of truth. Health Connect is the on-device aggregation layer for wearable data (WBL-01); the backend never talks to wearable vendors at MVP.

Fig 1 — System context. One client, one deployable, one relational source of truth.

Architecture rules

  • Backend modules communicate only through in-process interfaces — no shared table writes across modules
  • Module seams (identity / activity / social / messaging / moderation / privacy) are the future service boundaries
  • All external I/O behind interfaces; vendors (FCM, object storage) swappable
  • Every protected route re-checks authorization server-side (PRD §13)
  • Feature flags are server-driven config, evaluated per user (WBL-06, GRP-01)
  • Client works fully with no network: reads never block on HTTP

Android client architecture

Multi-module Gradle build: features compile against small core APIs, so tracking logic never depends on social code and MVP modules ship without v1.2 code paths.

Unidirectional data flow

  • UI observes a single immutable UiState per screen via StateFlow.
  • ViewModel reduces user events + repository flows into state; no Android framework types below the ViewModel.
  • Repositories expose Flows backed by Room. Network results land in Room first, then flow to UI — the UI never renders a network response directly.
  • Every screen state is one of Loading / Content / Empty / Error / PermissionDenied / Offline — the explicit-states requirement (DSH-04) is a type, not a convention.

App-level services

  • PermissionCoordinator — owns the explain-then-ask flow and denial recovery deep links (ONB-02/03).
  • StateBroadcaster — sync/source status shown wherever a total appears (TRK-06).
  • NotificationRouter — maps FCM data messages to Android channels; one channel per NTF category so OS-level toggles mirror in-app prefs (NTF-01).
  • AppLock — optional BiometricPrompt gate; keys in Keystore (ACC-07).
Section 6

Step-tracking engine

The hardest correctness problem in the product. The design separates capture (cheap, dumb, lossless) from interpretation (pure functions, exhaustively tested).

Capture pipeline

  • TYPE_STEP_COUNTER is a monotonic since-boot counter. The agent persists (boot_id, counter_value, elapsed_realtime, wall_clock, tz_offset) snapshots — raw, never interpreted at capture time.
  • Sensor batching (maxReportLatencyUs ≈ 5 min) lets the SoC buffer while the AP sleeps — the battery requirement (TRK-01) is met by hardware, not by a foreground service.
  • BOOT_COMPLETED + TIME_SET/TIMEZONE_CHANGED receivers write marker rows so interpretation can detect counter resets and clock changes (PRD §15 data-quality list).
  • Health Connect is polled by a periodic worker (15 min, constraint-free) and on app open; imports store provenance per record (WBL-02/04).

Interpretation: day bucketing & dedup

  • Snapshots become intervals: (source, start_utc, end_utc, steps, tz_offset_at_end). A counter delta across a boot marker is discarded (reset) — steps are never invented.
  • A day total is the sum of intervals bucketed by local date at the user's timezone when the interval ended — midnight rollover and DST fall out of bucketing rather than special cases (TRK-02).
  • Dedup rule (WBL-04): for any overlapping time range covered by more than one source, only the highest-priority source counts. Priority is user-ordered (default: wearable via Health Connect > phone sensor). Overlaps are resolved by interval subtraction — never by summing, never by max().
  • Each stored day total keeps per-source contributions so the UI can answer "where did this number come from?" (TRK-06).
dedup — pure function, property-tested
fun mergeDay(intervals: List<Interval>, priority: List<SourceId>): DayTotal {
    // 1. sort sources by user priority; higher priority claims time first
    // 2. sweep-line over the day: each instant is owned by exactly one source
    // 3. an interval's steps are distributed uniformly across its duration;
    //    only the owned sub-ranges contribute (partial overlap ⇒ pro-rated)
    // 4. result: total + per-source breakdown + list of resolved conflicts
    //    (surfaced in UI as "12:00–13:00 counted from Watch, not Phone")
}

// Invariants (property tests):
//  • mergeDay(single source)      == sum of its intervals
//  • total ≤ sum of all sources   (dedup never inflates)
//  • reordering priority never changes the covered time, only the owner
//  • intervals crossing local midnight split exactly at the boundary

Section 7

Offline-first synchronization

Two independent channels: a push channel (durable outbox of local mutations) and a pull channel (cursor-based delta download). Either can run without the other; both are idempotent and safe to retry.

Outbox (push)

  • Every local mutation writes its domain row and an outbox row in one Room transaction — atomically durable before any network attempt.
  • Each outbox entry carries a client-generated UUID used as the Idempotency-Key; server retries are exact-once in effect.
  • Drained FIFO per entity stream by a WorkManager unique worker; exponential backoff with jitter, network constraint, chunked batches.
  • Guest mode simply never schedules the worker; on registration the accumulated outbox becomes the history-migration upload (ACC-03).

Cursor sync (pull)

  • GET /v1/sync?cursor=… returns ordered change events across entities + next cursor; the client applies them transactionally and persists the cursor.
  • Server keeps a per-user monotonically ordered change log (Postgres bigserial per user stream) — cheap, replayable, no CRDTs needed.
  • Conflict policy: activity data merges via the §6 dedup (device data always wins over stale server state); settings/profile are last-write-wins per field with server timestamps; social state (friendships, memberships) is server-authoritative — the client never resolves it locally.

Fig 2 — Daily sync round-trip. Steps 1–2 work with no network; 3–8 run whenever connectivity allows.

Section 8

Data model

Server schema (PostgreSQL). The client mirrors the activity/goal/profile subset in Room with the same shapes plus outbox metadata. Conventions: UUIDv7 primary keys, created_at/updated_at everywhere, soft-delete (deleted_at) only where retention requires it, hard purge jobs otherwise.

Schema notes

  • activity_days is range-partitioned by month; hot queries hit ≤ 2 partitions
  • Per-source contributions kept alongside merged totals — “which source?” is one row read (TRK-06)
  • Consent, sessions, and audit are append-only; corrections are new rows, never updates
  • Contact-discovery hashes live in a purpose-scoped table with a TTL — never in users (FRD-02)
  • All foreign keys to users are ON DELETE handled by the deletion pipeline (§13), not by cascade surprises
  • Messages are stored per conversation partition; report/moderation state references messages by immutable ID
Section 9

API specification

REST + JSON over TLS, versioned under /v1. Errors are RFC 9457 application/problem+json. Cursor pagination (?cursor=…&limit=…) everywhere lists are returned. All mutating requests accept an Idempotency-Key; keys are cached in Redis for 24 h. Rate limits are token buckets per user + IP, returned in RateLimit-* headers.

Section 10

Leaderboards, ranking modes & fairness

Boards are materialized in Redis sorted sets and rebuilt from Postgres on demand — Redis is a cache, never the source of truth.

Score computation (LDB-02)

Goal % (default)min(steps / goal, 2.0) summed over period days ÷ eligible daysCapped at 200% per day so one huge day can't buy a week; rest days excluded from the denominator (GOL-03)
StepsΣ merged day totalsClassic mode, opt-in view

Privacy & virtual participants

  • Board reads run through a server-side privacy filter: opt-outs removed, approximate-visibility users bucketed (“~5,000–7,500”) before serialization (LDB-03, PRO-03). The raw value never leaves the server for a user who chose approximate display.
  • Virtual companions (LDB-05) are server-generated series with a deterministic daily curve per pace setting; rows carry isVirtual: true and clients must render the label — the API never disguises them.

Fairness pipeline (LDB-07, CHL-04)

  • Ingest checks (synchronous): reject impossible records — negative or absurd step counts (> 5 steps/second sustained), future timestamps, overlapping same-source intervals.
  • Pattern checks (async): daily totals over a configurable ceiling (default 60k), constant-cadence signatures, step bursts while the device reports stationary, repeated manual clock changes around challenge windows.
  • Flagged data stays in the owner's personal history but is excluded from boards and challenge standings pending review (“pending verification” badge). Review actions (clear / exclude / sanction) are audited; disputes follow the §13 corrections workflow.
Section 11

Messaging & realtime

Transport

  • One authenticated WebSocket per app session (WS /v1/ws), multiplexing chat, presence, and live challenge standings. Tokens are re-validated on connect and on a 10-min heartbeat.
  • Offline recipients get FCM data pushes; message history back-fills over the §7 cursor sync — the socket is an optimization, never the source of truth.
  • Delivery: at-least-once with client-side dedup on message UUID; ordering per conversation via server sequence numbers.

Safety at the write path (MSG-02/03/04)

  • Rate limits enforced before persistence: per-user, per-conversation, and burst buckets in Redis; violations return 429 problem+json with retry hints.
  • Block lists are checked at send time server-side — a blocked sender's message is rejected, not hidden client-side.
  • Reports snapshot the message content immutably at report time (edits/deletes can't destroy evidence); moderation actions write to the append-only audit log with actor, action, policy basis.
  • Text-only at launch: no media in chat = no CSAM/image-abuse surface until moderation capacity exists (PRD §19-7).
Section 12

Security architecture

Authentication

Sign in with Google (OIDC, nonce-bound) and email/password (Argon2id, breach-list check, verification required). Access JWT 15 min · refresh tokens rotate on every use with reuse detection → family revocation. Sessions registry backs “sign out all devices” (ACC-04). Enumeration-safe responses on register/recover.

Authorization

Every route declares a policy: resource ownership, friendship visibility, group role (member/moderator/admin), or platform-admin scope. Policies are unit-tested as a matrix; a route without a declared policy fails CI. Platform-admin actions require step-up auth and are fully audited (PRD §7.5).

Transport & storage

TLS 1.2+ only, HSTS, certificate pinning in the client. At rest: full-disk + column-level encryption for tokens and consent evidence. Client tokens in Keystore-backed encrypted storage; no secrets in SharedPreferences or logs.

Input & upload safety

Strict schema validation at the boundary (unknown fields rejected on writes); output encoding by serializer. Image uploads: type sniffing, re-encode to strip EXIF/GPS, dimension caps, malware scan before publish (PRD §13 file-upload controls).

Abuse resistance

Layered rate limits (IP → user → action). Friend-request and invite throttles. Idempotency keys prevent replay double-writes. WAF-level bot rules on auth endpoints. Suspicious-activity signals feed the §10 fairness pipeline and the trust-and-safety queue.

Supply chain & secrets

Dependency scanning + Renovate auto-PRs; SAST on every PR; secrets only in the cloud secret manager, rotated, never in the repo; signed releases with Play integrity checks. Third-party licence audit per release (SET-04).

Section 13

Privacy engineering

Consent & minimization

  • Consent records are append-only rows: (user, purpose, granted, policy_version, at) — the PRD's consent history (ACC-06) is a query, not a reconstruction.
  • Health data types are enumerated allow-list only (steps, distance at MVP); requesting a new type is a schema + review change, not a config flip.
  • Contact discovery (FRD-02): client hashes normalized numbers (salted, per-deployment); server matches against opted-in hashes, returns matches only, stores the uploaded set for max 24 h with a deletion endpoint. Raw contact lists never leave the device.
  • Analytics events pass a build-time schema linter: any event carrying free text or precise health values fails the build until reviewed (PRD §19-12).

Export & deletion pipelines

  • Export (ACC-05, HIS-07): async job assembles JSON + CSV into an object-storage bundle; signed URL, 7-day expiry, notification on ready. Includes activity, goals, achievements, profile, consent history.
  • Deletion: two-phase — immediate soft-lock (account unusable, hidden from all social surfaces) then hard purge after a grace window (working assumption 14 days, pending PRD §19-8 retention decision). The purge worker walks a registered manifest of user-data locations; an unregistered table with a user_id column fails CI.
  • Backups age out within the retention window; deletion completion is measured (PRD §17 trust metric “export & deletion completion rate = 100%”).
  • Messages authored by a deleted user are tombstoned (“account deleted”) to preserve conversation integrity for others — documented in the privacy notice.

Section 15

Observability

Traces & metrics

OpenTelemetry SDK on client and server; trace context propagated from sync worker through ingest to Redis update. RED metrics per route; USE metrics per dependency. SLO burn-rate alerts (fast+slow windows) for every §14 target.

Logs

Structured JSON, request-scoped IDs, no health values or message content in logs — a log-schema test enforces the redaction list. Client logs are local ring buffers attached to support reports only with user consent.

Product health

Crashlytics for crash-free sessions; Play vitals (ANR, wakeups) watched per release. Tracking-health telemetry (sensor gaps, boot recoveries, HC availability) is aggregated and anonymous — it measures the engine, not the person.

Dashboards ship with the feature: a PR that adds an endpoint without RED metrics and an alert rule fails review. On-call runbooks live beside the module they cover.

Section 17

CI/CD, environments & release gates

Pipeline (GitHub Actions)

  1. PR: lint + unit + Room migrations + screenshot diff + a11y checks + SAST + API schema diff — required, < 15 min
  2. Merge to main: full suite + Macrobenchmark + backend integration (Testcontainers) → staging deploy + internal track build
  3. Release branch: E2E device-lab run + load test + release notes → Play closed track
  4. Production: staged rollout 1% → 10% → 50% → 100%, auto-halt on crash-free or SLO regression; backend deploys blue-green with migration gating (expand → migrate → contract)

Environments & flags

  • dev (ephemeral per-PR backend) · staging (prod-shaped, synthetic data only) · prod. No production data in lower environments, ever.
  • Server-driven feature flags gate every phase feature (friends, groups, chat, providers) — v1.2 code can ship dark in the MVP binary.
  • Remote config carries fairness thresholds and diagnostics tuning so trust rules adjust without a release.
  • DB migrations are backward-compatible for one release window (expand/contract), so rollback is always possible.

Phase release gates (PRD §16)

  • P0 acceptance green · a11y verification pass · privacy checklist signed
  • v1.1+: abuse/rate-limit tests green; v1.2: moderation staffing + guidelines live (PRD §19-7)
